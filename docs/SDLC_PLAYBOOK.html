You, as a GitHub issue

Turn an idea into one testable user outcome. This is the spec every agent downstream works from.

Who
You. Never delegated.
In
A product idea
Out
Issue with who and state, action, outcome, acceptance criteria

Done when: Someone else could write the tests from it without asking you anything.

Steps
  1. Open a story from the template so every issue has the same shape.
  2. Write acceptance criteria as checkable lines. Each one becomes at least one test in stage 5.
  3. Include the failure cases, not just the happy path.
  4. Link it under its epic as a sub-issue.
Commands
gh issue create --template story --label story
Learn Faster: issue #42

Who and state: a learner partway through a lesson plan.

Action: after each lesson step, the tutor asks one short “Your turn” question. A grader scores the answer and returns a verdict and the gap.

Outcome: a correct answer moves to the next step. A partial or wrong answer gets a re-explanation of the named gap, then the question again.

  • ☐ Correct → next step
  • ☐ Partial or wrong → re-explain the gap, stay on step
  • ☐ Empty answer → can’t continue, clear message
  • ☐ Grader fails → friendly message, never a stack trace, step unchanged
Watch out

Vague outcomes like “better feedback”. Agents fill gaps with guesses.

Steps

  2. Debate the design. Push back until the trade-offs are clear.

Subagent tester, Sonnet, edits tests/ only

Write tests from the story alone, before any code. They check what was asked for, and the red tests become the coder’s target.

In
Issue body only, never the comments where research and plan live
Out
Committed tests that fail for the right reason

Done when: Every acceptance criterion has a red test.

Steps
  1. Run /test 42. The command passes only the number, so the planner can’t leak its assumptions.
  2. One test per acceptance criterion, plus edge cases.
  3. Mock every LLM call. Tests must not hit the API.
  4. Run them and confirm they fail because the feature is missing, not because of a typo.

Subagent coder, Sonnet, one per step

Implement one plan step at a time in a clean context, until its tests go green.

In
One step from the plan comment
Out
Green tests and one pushed commit per step

Done when: All tests green, one pushed commit per step.

↻ Runs until the tests pass. Product questions stop the run and go back to the planner.

Steps
  1. Branch once per story.
  2. Ask the main session to run the coder on one step.
  3. Read whole files as it works, not just the diff.
  4. If it returns a question, decide with the planner, update the plan, then rerun the step.
  5. Commit and push, then the next step in a fresh coder. In cloud, unpushed work dies with the session.

Subagent cleanup, Sonnet, once a week

Fight bloat across the whole codebase once a week instead of polishing every PR. Agents add code faster than anyone removes it; this is where it gets removed.

In
Whole repo, plus the week’s open tech issues logged by coders
Out
One cleanup PR, a triaged tech backlog, a pruned CLAUDE.md

Done when: one green PR that shrinks the codebase, and every tech issue is fixed, turned into a story, or closed.

Steps
  1. Branch once for the week.
  2. Run the free deterministic tools across the repo.
  3. Cleanup subagent works through the findings and open tech issues, one commit per theme, tests after each.
  4. Triage what’s left: fix now, make it a story, or close it.
  5. Prune CLAUDE.md: drop lines that no longer earn their place, keep it under 200.
  6. Docs subagent checks docs/ against the code for drift.
  7. Same review as any PR: CI, Codex, you merge.
Commands
git switch -c cleanup/$(date +%G-w%V)
ruff check . --select F401,F841,ERA001 --fix
vulture src/ --min-confidence 80
npx jscpd src/
gh issue list --label tech --state open
> Use the cleanup subagent on the findings and open tech issues.
pytest
gh pr create --fill --label cleanup

Where state lives

Every cloud session starts from a fresh clone. Anything not in GitHub is gone when it ends, so GitHub is the state store. Any session, cloud or local, can pick up a story by reading its issue.

StateLives in
SpecIssue body
ResearchIssue comment
PlanIssue comment
Current stageIssue label stage:*
Tests and codeBranch commits, pushed after every step
ReviewPR comments
Tech debtIssues labelled tech
LessonsCLAUDE.md, committed

Inside one session, subagents share the VM’s files, so scratch files are fine. Push anything the next session needs before this one ends. The tester reads only the issue body, so research and plan in the comments never reach it.

Rules that keep quality up and tokens down
  1. State lives in GitHub: the issue, its labels, the branch and the PR. Push before any session ends.
  2. Bloat is handled weekly, not per PR. Coders log mess as tech issues; the weekly cleanup consumes them.
  3. Opus plans at high effort; /model opusplan automates the switch. Sonnet researches, tests and builds, at high or max effort. A tight plan is what lets Sonnet match Opus. Escalate to Opus for subtle bugs or multi-file refactors.
  4. Stay under about 60% of the context window. If a phase needs more, split it.
  5. CLAUDE.md answers “how do we work here?”, never “what are we building now?”. Every subagent loads it, so feature details there leak bias and multiply cost.
  6. The tester gets the issue number, never a summary from the planner.
  7. Later: label an issue ready and the Claude Code GitHub Action runs the same agents with no relay.
